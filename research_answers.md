# Research Answers

## 1. HTTP State Preservation: Authentication and Session Management

Django preserves user state across stateless HTTP requests by combining cookies, server-side sessions, and authentication middleware. Each request is independent, so the server cannot "remember" a user unless a unique identifier is sent with every request. Django solves this by placing a session key in a cookie (`sessionid`) and storing the session data on the server (commonly in the database). During login, Django validates credentials, attaches the authenticated user's ID to the session, and sends the session cookie back to the browser. On later requests, middleware reads that cookie, loads the session data, and populates `request.user`, allowing authorization checks and personalized responses. Session expiry and rotation policies reduce fixation and hijacking risks, and `HttpOnly`, `Secure`, and `SameSite` cookie flags add browser-level protection. CSRF tokens are also used for unsafe methods (POST, PUT, DELETE) so authenticated sessions cannot be abused by cross-site form submissions. Some modern systems use stateless JWT tokens, but Django's default session approach remains practical and secure for many web apps because revocation, expiry, and permission updates are easier to control centrally.

## 2. Django Database Migrations to MariaDB

Migrating a Django project to MariaDB typically starts with installing and validating a MariaDB-compatible driver such as `mysqlclient` (or MariaDB Connector/Python, depending on environment support). Next, create the target database and user in MariaDB with least-privilege permissions (for example, SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX on a specific schema). In `settings.py`, configure `DATABASES['default']` with `ENGINE = 'django.db.backends.mysql'`, plus host, port, database name, username, password, and optional connection options (character set `utf8mb4`, SQL mode, SSL, etc.). Then run `python manage.py makemigrations` to generate migration files from model changes and `python manage.py migrate` to apply them to MariaDB in dependency order. For production, teams usually run `python manage.py showmigrations` before deployment, back up the database, and execute migrations in CI/CD with rollback plans. If moving from SQLite to MariaDB, schema migration is straightforward, but data migration may require dump/load scripts or custom migration operations. The migration framework is valuable because schema history is versioned, repeatable, and auditable across development, staging, and production servers.
